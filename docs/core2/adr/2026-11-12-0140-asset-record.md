# Use one Project-owned Asset identity and nested repository spec

## Status

Decision disposition: accepted, deferred, superseded. Individual keyed statements below control mixed records.

Implementation: **unimplemented** at D1. Scope: foundation.

ADR created: 2026-11-12-0140 UTC. Original decision date: unknown; filename time is promotion time, not a reconstructed decision date.

## Context

A wrapper plus a Repository record would duplicate one configured target. Asset means durable Project allocation, not one Delivery target or produced Artifact.

## Decision

<a id="asset-01"></a>

### ASSET-01 — Asset identity and shape

**Disposition:** accepted. **Implementation:** unimplemented.

Use one Project-owned Asset record: `id`, `projectId`, `spec`, `created`. Repository spec is `{ type: "repository", source: { provider: "github", owner, name, secretId } }`. No separate Repository identity, wrapper, allocation model, root type/source peers, title, host field or copied Project/Secret data. projectId is authoritative ownership; child lists are derived.

**Recorded rationale:** One record avoids one-to-one wrapper consistency and supports durable configuration.

<a id="asset-h01"></a>

### ASSET-H01 — Historical Repository and Source names

**Disposition:** superseded. **Implementation:** unimplemented.

Earlier identified Repository records and the working unified name Source are superseded by Asset. Project Source classification is now Project type; spec/source replace proposed details/config naming. Resource and Target were rejected as overly broad or too tied to one Delivery.

**Original rationale:** The cited record preserves the earlier choice and its reversal but does not record an original adoption rationale; no successor rationale is attributed to it.

**Reason superseded:** Asset conveys durable Project allocation independently of a particular Delivery; one identified record avoids a Repository wrapper/second identity. Resource was too broad and Target too tied to Delivery.

<a id="asset-02"></a>

### ASSET-02 — Creation-time credential binding

**Disposition:** deferred. **Implementation:** unimplemented.

Defer Asset rebindSecret/rebind/generic update or patch. secretId is selected at creation and remains fixed through the current API. Remove updated with no alias/null/alternate stamp. Updating the same Secret’s value remains supported without altering Asset created/bindings or Project attribution.

**Recorded rationale:** No supported Asset mutation currently needs update attribution.

<a id="asset-h02"></a>

### ASSET-H02 — Historical rebinding

**Disposition:** superseded. **Implementation:** unimplemented.

Previously accepted credential rebinding preserved Asset target/identity/ownership and atomically wrote spec.source.secretId/updated after same-Portfolio validation. Last successful commit won without a stale-binding guard; same binding also applied and recorded, returning Asset directly. No credential resolution or stamp cascade. This is now parked, not available.

**Original rationale:** Credential selection could change independently of immutable target identity, for example from a shared to a dedicated Secret without rewriting existing work. Simple atomic last-commit-wins updates deliberately accepted stale-screen overwrites without an expected-binding guard.

**Reason superseded:** The user deferred credential rebinding and removed Asset.updated instead of retaining an alias or generic update substitute. No further original reason for the scope cut is recorded.

<a id="asset-h03"></a>

### ASSET-H03 — Historical already-bound refusal

**Disposition:** superseded. **Implementation:** unimplemented.

The earlier already-bound exception was superseded by same-binding apply-and-record before rebinding itself was deferred. `asset-already-bound` is not a current error.

**Original rationale:** The cited record preserves the earlier choice and its reversal but does not record an original adoption rationale; no successor rationale is attributed to it.

**Reason superseded:** The later common apply-and-record rule accepts identical valid binding writes and records attribution instead of requiring an already-bound error or equality no-op.

The decision record does not claim runtime verification. Foundation implementation tasks must prove applicable behavior; paused scope requires separate authorization.
