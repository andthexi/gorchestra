# Let Hermes own ongoing conversation

## Status

Decision disposition: accepted, superseded. Individual keyed statements below control mixed records.

Implementation: **unimplemented** at D1. Scope: outside foundation scope; paused and unimplemented.

ADR created: 2026-11-12-0140 UTC. Original decision date: unknown; filename time is promotion time, not a reconstructed decision date.

## Context

The intended Consumer already provides the Hermes chat conversation; routing every reply through Core would duplicate its authority and lifecycle.

## Decision

<a id="hermes-02"></a>

### HERMES-02 — Hermes owns ongoing chat

**Disposition:** accepted. **Implementation:** unimplemented.

All ongoing user/agent messages and conversational runs stay in Hermes. Core does not relay messages or schedule every reply and has no per-message outbox/save-before-send mechanism. On successful Core acceptance the Consumer closes/redirects chat view after commit; no transcript deletion or provider session-close assumption. Initial session/start and autonomous Core-initiated runtime operations remain separately scoped.

**Recorded rationale:** Typed proposal storage and human acceptance, not interpreting chat, is the Core boundary.

<a id="hermes-h01"></a>

### HERMES-H01 — Historical Core chat relay

**Disposition:** superseded. **Implementation:** unimplemented.

The earlier submit-through-Core ongoing-chat choice is superseded because it assumed the wrong interface ownership. Save-before-send/outbox was only a proposal and was never selected.

**Original rationale:** The source says submit-through-Core was based on an incorrect model of the intended interface. It records no further original justification, and the save-before-send/outbox suggestion was never selected.

**Reason superseded:** Hermes owns ongoing conversation; Core handles typed proposals and human-authorized acceptance rather than relaying every chat turn.

## Consequences

Core stores structured proposals and accepts human actions, not chat messages/outboxes. Successful acceptance precedes UI close/redirect and implies no transcript deletion.

The decision record does not claim runtime verification. Foundation implementation tasks must prove applicable behavior; paused scope requires separate authorization.
