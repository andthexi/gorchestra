## Context

Consumers need explicit safe success/failure outcomes across factory, lifecycle and domain operation boundaries.

## Decision

<a id="result-01"></a>

### RESULT-01 — Result envelope

**Disposition:** accepted. **Implementation:** unimplemented.

Use `Result<T,E> = { ok: true; value: T } | { ok: false; error: E }`; asynchronous operations return a promised Result, while as is synchronous. Expected failures are values, not normal Promise rejection. Concrete success/error branches are runtime validated; no live facade is serialized through a subprocess.

**Recorded rationale:** Explicit success/failure narrows consumer usage without equating safe error payloads with rollback proof.

## Alternatives and supersession

- **RESULT-01:** No additional mechanism is selected.

## Consequences

Result is a discriminated data contract, not raw exceptions or a serialized live facade. Concrete branches remain validated and operational failure does not imply replay safety.

The decision record does not claim runtime verification. Foundation implementation tasks must prove applicable behavior; paused scope requires separate authorization.
