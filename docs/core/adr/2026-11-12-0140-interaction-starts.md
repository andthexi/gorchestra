# Persist interaction starts before contacting the harness

Accepted; **unimplemented**. Expedition, runtime and downstream work remain paused.

Rolling back local startup cannot undo a harness session and can erase the identifier needed to recover its association. A user-authorized domain action therefore creates and commits the AgentInteraction, its Core-supplied identifier and exact resolved creation request before calling the harness to create a session. Only successful session creation permits Core to set the started marker and persist the acknowledged session association in a later transaction. The first transaction also reserves the target/purpose slot: only one unfinished interaction may occupy it, whether awaiting startup or already started. A crash or uncertain response leaves the saved record with the marker unset; explicit retry uses its saved identifier and request rather than rebuilding context or creating a replacement. This accepts an observable intermediate state instead of an all-or-nothing local start, without a background queue or automatic recovery.

The saved creation request excludes tool definitions and handlers: Core infers tools from the persisted interaction purpose at runtime rather than storing a separate tool list. The harness can begin execution before Core persists its acknowledgment. Once the starting record is committed, interaction-bound tools may read permitted context; rejecting all early calls would discard useful work during that acknowledgment window. These calls neither confirm startup nor advance the target's domain state. When proposal support is added with Expedition, unaccepted submissions may also arrive during startup, while acceptance remains blocked until startup is confirmed; no proposal behavior is delivered by the initial interaction infrastructure.

An uncertain harness request is not presumed failure. The Consumer-supplied harness integration owns duplicate prevention: identical creation requests under the same Core-supplied identifier return the same session without repeating initial execution, while changed inputs under that identifier fail. Core trusts this integration contract rather than implementing duplicate prevention, tracking retention windows or probing the guarantee. An explicit retry retains the original identifier and creation inputs, never silently creates a replacement. This contract does not introduce automatic retries, Core Session/Run domain models or an exactly-once guarantee for external tool effects.

The started record atomically contains the confirmation timestamp and harness session reference, rather than a boolean that can disagree with separately written session data. It records successful session creation, not the harness's current execution state. Separate explicit transactions cover the database phases, with no transaction or database lock held across the harness call; the saved target/purpose reservation persists independently. For MVP, Consumer maintenance draining covers the whole startup operation, so no shared maintenance-coordination lock is required around its database phases. Failure or uncertainty leaves the interaction and its reservation intact. Repair, timeout-based release and repair-driven terminal error transitions are deferred; session lookup does not perform those mutations. Import makes no harness calls, and local rollback cannot stop a session that the harness already created.
