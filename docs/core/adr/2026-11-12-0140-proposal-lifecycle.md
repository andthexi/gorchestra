# Separate stored proposals from human acceptance

Accepted architecture. Delivery scope is tracked under [Expedition and proposals](../FUTURE.md#expedition-and-proposals).

An agent can propose work but cannot supply its own authority or substitute content for what a human reviewed. Tools therefore save immutable unaccepted versions in a trusted Consumer-bound AgentInteraction and return immediately; separate human acceptance loads the exact current stored proposal and applies domain changes, instead of holding a transaction across review, accepting a replacement payload or deriving approval from chat. Only the latest eligible version can be accepted, rejection never revives an older version, and accepted history cannot be rewritten by later runtime observations. Rejection preserves the rejected version as ineligible and leaves the same interaction/session open for a new proposal version; it neither closes the interaction nor automatically sends feedback to the harness.

Each version contains the complete proposed result, not a patch to an earlier proposal, so validation and human review do not depend on reconstructing proposal history. Submission identifies the expected current proposal version, and Core atomically appends only if that expectation still holds; competing submissions based on the same version cannot both succeed. A conflict requires reading the current version before a deliberate resubmission, not automatic retry or rebasing. A new version replaces the proposal under consideration; it does not imply replacement of all existing target-domain records, whose changes remain governed by the purpose-specific acceptance operation.

Agents may submit new versions during human review. Acceptance names the exact reviewed version and atomically checks that it is still the latest eligible proposal before applying domain changes and closing the interaction. A newer submission makes acceptance of the older version fail as stale; Core never substitutes the newer version for the one reviewed. Closure blocks new bound Core tool calls, including reads, while already-admitted reads may finish; strict coordination of in-flight tool writes with closure is [deferred](../FUTURE.md#tool-write-and-closure-coordination). Normal Consumer-authorized queries and the harness session/transcript remain available; retaining a tool binding cannot grant new admission after closure.

Consumer binding selects the interaction and Core derives its target; model arguments cannot choose arbitrary actor, approval or target IDs. AgentInteraction owns integration state, not transcripts or target facts, so runtime termination is not domain completion and acceptance may precede it; repeated acceptance returns an already-accepted error rather than replayed success. Human proposal acceptance and embedded Evidence supply discovery review without a parallel Artifact/Review layer, while relevant domain/provenance gates—not every unrelated Map change—control staleness.
