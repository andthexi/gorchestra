# Core Documentation DOX

## Purpose

The `docs/core/` tree documents domain language and architectural decisions for the current Core implementation at `libs/core` (`@gorchestra/core`).

## Ownership

- `CONTEXT.md` owns domain terms and relationships in glossary form.
- `adr/` owns individual architectural decisions. Do not add an ADR README, decision inventory or standalone contract specification.
- The [package README](../../libs/core/README.md) and [source instructions](../../libs/core/AGENTS.md) own implemented usage, schemas, API details and verification guidance.

## Local Contracts

- Read [context](CONTEXT.md) and affected [ADRs](adr/) before changing language or decisions.
- Use unnumbered Core/domain names in prose and code. The package is `@gorchestra/core`; its documentation lives in this directory.
- Describe current boundaries and accepted designs without retired implementation comparisons or coexistence/cutover instructions. Consumer remains an architectural role; no Consumer application is implemented.
- Offer an ADR only if **all three** hold: it is hard to reverse, surprising without context, and the result of a real tradeoff with genuine alternatives. If any is missing, skip it. Acceptance, importance, task delivery, deferral or a future review checkpoint alone is insufficient.
- Prefer a short title and 1–3 sentences for context, decision and why. Add status, options or consequences only when useful. Keep the `YYYY-MM-DD-HHMM-slug.md` filename convention.
- Keep decisions self-contained with their context, chosen approach, tradeoff and limits. Include substantive evidence or cite maintained source material; never use temporary planning notes as citations. Preserve actual replacement links without reproducing intermediate planning exchanges or inventing alternatives.
- Keep acceptance separate from implementation status. Accepted designs do not authorize paused Expedition/downstream work or a new Consumer application.
- Agent Interactions are Core-created domain records paired with one harness session for their lifetime through a Consumer-supplied dependency. A new purpose requires a new interaction/session; missing or failed sessions must not cause implicit replacement. Keep Core proposal/domain state distinct from harness-owned execution and transcripts; this boundary is accepted, not yet implemented.
- Supply the harness through public `CoreDependencies.harness` in the initial infrastructure delivery, before Expedition integration. This dependency does not expose generic interaction creation or acceptance to Consumers.
- Do not persist or require a harness-instance identity or session-namespace identifier. Resolve stored session references through the configured harness dependency; selecting the correct dependency remains the Consumer's responsibility, including after import.
- Route ongoing Consumer conversation directly to the harness, not through Core. Keep proposal submission and human-authorized domain operations separate from conversational messages.
- Core owns purpose-specific session instructions and resolves domain context before invoking the harness dependency. The dependency adapts the resolved request to the harness without loading authoritative domain records or deciding domain behavior.
- Interaction-bound reads return current permitted domain data, with record/version identities where applicable; they do not rewrite the saved startup request. Acceptance still rechecks purpose-specific domain prerequisites rather than trusting startup context or prior reads.
- Core infers each interaction's Core tools from its persisted purpose at runtime and binds their authority to its target and purpose; the dependency exposes them through the harness. Do not persist tool definitions, schemas or handlers, or accept a separately selected per-interaction tool list. Never let agent arguments select another interaction's authority or expose human-only acceptance as an agent tool.
- Consumers control harness-native tools and sandbox permissions. Do not introduce harness-specific permission management into Core or treat native-tool access as permission to bypass Core domain operations.
- Keep the Consumer-supplied harness dependency a generic adapter for session-level operations. The harness manages its internal runs; do not infer a Consumer/Core run controller or separate run-submission API from session creation.
- Keep harness session lookup by ID read-only. Lookup does not repair an interaction, release its reservation or transition it to terminal error; import and ordinary domain reads do not trigger harness checks.
- Trust the Consumer-supplied harness integration to prevent duplication: identical creation requests under the same Core-supplied identifier return the same session without repeating initial execution, and changed creation inputs under that identifier fail. Core reuses the saved identifier and exact request on explicit retry; do not add Core-owned deduplication, retention-window tracking or probes to verify that guarantee. Retry remains explicit, never automatic.
- A user-authorized domain action creates and commits the interaction's identifier and exact resolved creation request before calling the harness to create its session. The saved request excludes tools, which Core infers from the interaction's purpose. After success, atomically persist `started` as an embedded record containing the confirmation timestamp and harness session reference, never a boolean with independently nullable peer fields. It records startup success, not whether the harness is currently executing. Preserve uncertain starts for explicit retry with the saved request; do not add a background queue.
- Use separate explicit transactions for interaction startup's database phases, with no transaction or database lock held across the harness call. Do not add shared maintenance-coordination locks to these phases for MVP; Consumers drain whole in-flight operations before maintenance. Preserve atomic target/purpose reservation guards independently of maintenance coordination.
- When session creation fails after the interaction is committed, return a safe error type and the saved interaction's ID so the Consumer can identify it for explicit retry. Never expose raw harness diagnostics or imply that the committed interaction was rolled back.
- After the starting record commits, permit interaction-bound context reads even before acknowledgment. These calls neither confirm startup nor advance target state. Proposal-related early calls belong to the later Expedition integration, not this infrastructure delivery.
- Enforce one unfinished interaction per target and purpose across clients. Awaiting-confirmation and startup-confirmed interactions reserve the slot; a second start fails rather than reusing it implicitly. Explicit startup retry addresses the existing interaction, while different targets remain independently eligible.
- Initial AgentInteraction scope excludes abandonment, repair operations and repair-driven terminal error transitions. If session creation fails or its outcome is unknown, leave the started marker unset and retain the saved interaction and target/purpose reservation. Do not add timeout-based release, replacement or automatic recovery; repair semantics are deferred.
- Deliver AgentInteraction infrastructure independently of Expedition. Proposal schemas, collections, versioning, submission, review, acceptance/rejection operations and their tests are deferred to Expedition integration, alongside Expedition schemas, charting, Question research, Blueprint drafting and Delivery execution. Do not add proposal placeholders to this infrastructure delivery.
- Keep generic interaction creation and lifecycle controls internal to Core, for later target-specific domain operations. The calling Core domain operation supplies the already-resolved target, purpose, instructions and context, not a tool list. Shared interaction infrastructure persists the request, uses Core's purpose-inferred tools for session creation and records `started`; resolve those tools before invoking the harness dependency. Consumers supply the harness dependency, not arbitrary domain definitions or acceptance handlers. Verify session lifecycle and tool-binding infrastructure with test-owned definitions and real storage, without implementing proposal behavior or placeholder Expedition features.
- Completion rejects further calls to all interaction-bound Core tools, including reads, but does not close the paired harness session or delete its transcript. Enforce this against persisted lifecycle state even when the harness retains an earlier tool binding; separately Consumer-authorized queries remain available. A late startup acknowledgment cannot reopen a completed interaction or reclaim its released reservation.
- Preserve the accepted [proposal lifecycle](adr/2026-11-12-0140-proposal-lifecycle.md) as later Expedition design, not an acceptance criterion for the initial AgentInteraction infrastructure.
- MVP Snapshot import preserves AgentInteraction records, saved startup requests and original harness-session associations rather than making them inert; proposal history will join this contract when delivered with Expedition. Restore access and startup-retry eligibility according to the imported lifecycle state and ordinary authorization checks; do not call the harness during import. Source and destination may therefore refer to the same session. Import-time session isolation and explicit detachment/rebinding are post-MVP improvements, not current implementation requirements.

## Work Guidance

- Keep `CONTEXT.md` a glossary, not a schema/API specification, task checklist or verification report.
- Remove automatic whole-handler transactions from the shared operation runner, not only for interaction startup. Handlers explicitly call a shared transaction helper around work that must commit together; the helper aborts its transaction on a failed Result or exception without parsing Core-authored Results. This accepted change is unimplemented; preserve required domain atomicity, external-boundary validation, storage admission and safe errors rather than treating wrapper removal as permission for partial atomic updates. Do not infer rollback of previously committed phases from a later failure Result.
- Validate data entering Core from external boundaries through Valleyed, including Consumer inputs, storage reads and write-returned data, harness/provider responses and imported payloads. Trust typed Results assembled inside Core from validated data rather than revalidating them in the runner or transaction helper. Construct the declared public values and safe errors explicitly; do not rely on final output parsing for transformations, field stripping or Secret protection. Expose public operation Result and error pipes for Consumer-side validation without exposing internal handlers or storage schemas. This accepted boundary-only validation design is unimplemented; behavior tests must verify returned values conform to the public contracts.
- Export those pipes in a separate public contracts tree mirroring the operation namespaces, usable without creating or opening a Portfolio. Access to validation contracts grants no operation authority and exposes no internal handlers or storage resources.
- Cover every public Result-returning operation in that contracts surface, including opening, setup, migration, attribution binding, shutdown and Snapshot export/import as well as domain operations. Include each operation's complete error union, not only handler-specific errors.
- Success pipes for live Portfolio/lifecycle handles validate the expected instances in-process and preserve their identity without cloning, invoking methods or performing I/O. They neither serialize handles nor reconstruct them from JSON, and validation does not certify that a handle remains open or usable later.
- Deliver the accepted work as two separately reviewed Changes: first the Core foundation refactor (explicit transactions, boundary-only validation, public contracts and Consumer-owned maintenance coordination), then dependent AgentInteraction infrastructure. This sequencing does not authorize Change creation or execution before their respective reviews.
- Distinguish Core-owned Stored Secret Values and Portfolio Secret Protection from Consumer encryption-key provisioning. Core-owned protection and Snapshot export/import are implemented; the package README owns usage and verification scope. Do not describe Consumer codec callbacks or external-store references as the current Secret API.
- Portfolio Import requires a ready Portfolio and means atomic replacement with preserved imported identities and relationships, not initialization or record merging. Snapshots always include Secret values under passphrase encryption, never the Portfolio encryption key. Import uses the destination's opening key or explicit plaintext mode, never a per-import replacement key.
- Snapshots carry the source's final validated catalog migration ID, not a restorable migration ledger. Export captures that ID with the data; import revalidates destination history inside the replacement transaction and requires an exact recognized ID match before writes. Never infer migration order from timestamps, overwrite the destination ledger or convert mismatched Snapshots.
- Import validates payload and record schemas, not cross-record relationships or graph consistency; do not add duplicate-ID constraints, deduplication, a relationship audit or data repair. Preserve exported domain data except conversion of Audit Stamps to imported attribution and the agreed Secret-value reprotection under the destination's opening key/mode. Snapshot authentication, migration compatibility and atomic storage-failure handling still apply. Schema-valid data is not a certification of relational integrity.
- Imported Audit Stamps use `{ src: 'imported', at, iat }`: preserve the original `at`, remove `by`/`cid`, and refresh `iat` to this import's time on every import, including already-imported stamps. Subsequent local operations create ordinary local stamps.
- MVP Snapshot export/import processes complete serialized strings in memory without a Core-enforced size cap or streaming. Document memory exhaustion and long Consumer maintenance pauses as limitations; bounded-memory processing and size controls are post-MVP work.
- Remove Core's explicit maintenance-coordination locks from opening, ordinary operations, setup, migration, export and import, and remove the corresponding adapter lock-capability requirement. This accepted change is unimplemented; do not replace those locks with local locks, queues or an optional-lock fallback. Consumers serialize maintenance actions and exclude ordinary access and new client opening while maintenance runs. Explicit transactions and domain-specific concurrency protection remain separate requirements; this decision does not disable backend-internal transaction locks.
- For MVP, Consumers coordinate migration, export and import across all clients sharing a Portfolio: prevent new ordinary access, drain whole in-flight operations (including pending harness calls and their database continuations), and keep access paused until maintenance settles. This includes interaction-bound Core tool calls; it does not require closing harness sessions. Migration requires stopping existing clients and reopening compatible clients afterward. Core validates native history at opening and explicit setup/migration rather than on every ordinary domain operation. These changes are unimplemented; Core-managed maintenance draining/exclusion is post-MVP. Preserve local shutdown admission, external-data validation, domain concurrency guards, explicit atomic transactions and Snapshot compatibility checks; do not claim protection against a Consumer violating the maintenance protocol.
- Document working package usage alongside source changes. Do not move unimplemented method tables or implementation plans into the glossary or a renamed catalog.
- Prefer source/context links over duplicating detailed contracts across documents.
- Keep the Equipped choice and dependency-owned storage responsibilities in the [storage foundation ADR](adr/2026-11-14-1432-equipped-storage.md); package usage documents Core-owned behavior and Consumer obligations rather than repeating dependency guarantees.
