# Core engineering guide

## Package boundaries

- This private package is `@gorchestra/core` at `libs/core`, the repository's sole implementation package. Native storage opening, explicit whole-catalog setup and pending-suffix migration, private state views, shared shutdown, synchronous attribution binding, encrypted whole-Portfolio export/atomic import, Project/Secret create/find/list, Secret value replacement/usages, Project-scoped Asset create/find/list, Memory create/find/list and Revision create/find/list are implemented alongside primitives, domain models, Portfolio Secret Protection and history classification. The listed operations and shared-boundary coverage are implemented. Expose no placeholder methods.
- Validate dependencies with Valleyed without copying the native adapter or invoking the resolver. Secret dependencies contain only `encryptionKey: string | null`; null explicitly selects plaintext storage and strings must be canonical base64 encoding exactly 32 bytes.
- Preserve released migration IDs and literal changes independently of current model schemas; append new entries in ID order. Keep native builder validation authoritative. Validate all raw history entries before duplicates, unknown IDs and prefix membership; return type-only history errors without repair. Native InMemory catalog smoke tests do not establish lifecycle atomicity or resolver/isolation qualification.
- Admit adapters by declared capabilities, never database names. `CoreDependencies<A>` requires a single nonunion adapter type, checks catalog-compatible methods and definite field-name tuple slots, and keeps the resolver specific to `A`; callers must narrow before constructing the dependency pair. Widened arrays cannot prove support. After admission, deliberately use fixed `StorageAdapter` types in the owner, native Repo/Migrator and catalog, and nongeneric lifecycle views. Capture the original adapter/resolver pair; treat resolver results as opaque internally and do not manufacture configurations, re-pair callbacks or cast an existing Repo. Reject missing, malformed or empty runtime field declarations before startup without copying the adapter or revalidating the catalog. Keep native builder validation authoritative.
- Use unnumbered Core/domain identifiers such as `CoreDependencies`, `PortfolioClient` and `Portfolio`. The package is `@gorchestra/core`; current documentation lives in `docs/core/`.
- Read [package status](../../libs/core/README.md), [domain context](CONTEXT.md), and [ADRs](adr/) before implementing a slice.

## Local contracts

- Model modules own Equipped schemas; derive record pipes and types from those fields. Validate external data before use, preserve safe public projections and error payloads, and never expose raw secrets or diagnostics. The [operation boundaries](BOUNDARIES.md) define validation and response construction.
- Keep native Repo visible in operations rather than behind a recursive facade. Preserve external-boundary validation and explicit atomicity guarantees. Export declarations only for actual cross-module/public needs; never expose raw handlers, protected storage schemas, test hooks or internal constructors.
- Setup and migration remain explicit and whole-run atomic, with authoritative history classification and final raw-ledger confirmation before issuing a ready view. Preserve history-first refusals, exact rollback recognition and safe cleanup failure precedence without implicit repair or retry.
- Do not restore removed implementations or import temporary planning notes as code. New Consumer implementations and any legacy conversion or compatibility shim require explicit approval.
- Keep dependency declarations as `latest`. Global `pnpm-workspace.yaml` overrides own Equipped and Valleyed resolution, including transitive installs. Do not add package-specific exceptions or local dependency paths.
- The [storage foundation ADR](adr/2026-11-14-1432-equipped-storage.md) owns the Equipped rationale and dependency guarantees. Keep package documentation focused on Core behavior and Consumer responsibilities.
- Secret creation generates one ID before protecting the exact nonempty value and inserts one complete schema-owned row. Metadata reads validate full stored records before safe projection and never decrypt values.
- Secret value replacement validates the full required stored row before protecting with its existing identity. Write only `value` and `valueUpdated`, never a stale whole-row copy; preserve title/creation and apply identical accepted values with a fresh nonce. Null native update output is `invalid-output`, not optimistic success. Return parsed safe metadata only after commit.
- Asset creation requires full valid Project/Secret records before the scoped candidate read and validates all candidates before case-insensitive ASCII owner/name comparison. Preserve casing and ignore Secret ID for duplicate identity; concurrent uniqueness is not guaranteed. Validate an Asset before its ownership check; mismatch is not-found(asset). Asset lists/usages require their parent even when empty, return complete ID-sorted full Assets from native scoped queries, and perform no Secret decryption or provider calls. Derive usages from nested references, never stored reverse data.
- Memory creation requires explicit nullable parentage, validates any nonnull parent before writes, and inserts Memory plus Revision 1 in one operation transaction with two generated IDs, separate explicit-ID slots and one stamp. Keep Memory compact and parentage/creation fixed. List roots/direct children with native nullable equality, not missing-field matching; require nonnull parents even for empty lists. Exact Revision find uses only revisionId; full history requires a valid Memory and sorts by version. Validate every selected row without repair, recursive expansion or Secret decryption.
- Revision append validates full Memory, checks mismatch before matching-version exhaustion and allocates a successor/ID only afterward. Use native many-update with ID and typed nested version equality; never guarded one-update or an ID-only fallback. Validate the entire update array: zero is conflict, multiplicity/corruption is invalid-storage-output, exactly one permits the full snapshot insert in the same transaction. Update only the summary, preserve parent/creation/history, apply same-content writes and never expose actualVersion or retry implicitly. Sequential write-guard tests are not overlap-isolation acceptance.
- Reuse `storage/schema/index.ts` for schema-derived validation and invocation-local explicit IDs; its neighboring `index.test.ts` owns integration coverage. Native primary-key generation requires the slot even when create input includes an ID. Stored validation must not apply create defaults or caller-attribution defaults; keep nested fields intact and select public Secret fields explicitly.
- Keep lifecycle constructors non-public and return only established state-specific capabilities. One private owner retains storage/admission/cleanup; Consumers receive attribution-bound domain operations without lifecycle controls.
- Derive bound operation signatures and the runtime tree from normalized definitions. Preserve accepted-versus-parsed pipe types and zero-argument leaves; prevent handler inference from widening sibling pipes. Bind immutable copied attribution through closures without runtime freezing. Generate one ID per created record and one UTC stamp per invocation. Recognize rollback only by the invocation's private signal or one supported native session wrapper; do not match messages or arbitrary cause chains.
- Snapshot import must preserve atomic replacement, identities, schema-owned attribution conversion and Secret reprotection. See the [package README](../../libs/core/README.md#encrypted-portfolio-snapshots) for implemented behavior and [operation boundaries](BOUNDARIES.md) for coordination contracts.
- Use `<boundary>/index.ts` with neighboring `<boundary>/index.test.ts`; operation namespace indexes compose actual leaves. Keep small pure-helper runtime tests in their owning modules with `if (import.meta.vitest)`. Do not create empty public namespaces or duplicate a hand-maintained operation type registry.
- Exercise the public `@gorchestra/core` package entry in the real lifecycle tests; do not replace package-resolution coverage with a relative import or type-only test.
- Keep owning documentation and code synchronized within each Change. Changes track implementation progress; documentation describes the settled contracts directly.

## Agent Interaction

AgentInteraction is a Core domain model for one target and purpose, not a feature owned by a particular target domain. Core owns its identity, lifecycle and authority; its paired harness session owns execution and transcripts. A new purpose requires a new interaction/session pair, not repurposing an existing one. See [context](CONTEXT.md) and the [startup rationale](adr/2026-11-12-0140-interaction-starts.md).

Keep the reusable model, migration, find/run/repair operations, tool definition and invocation infrastructure, Snapshot handling and reservation behavior separate from production purpose variants and tools. Production purposes and tools arrive with their owning domain operations; do not invent a production purpose solely to exercise the infrastructure or expose Consumer registration as a substitute. Without a supported purpose supplied by a domain operation, Consumers cannot create a real interaction. Use concrete purpose handling rather than a purpose-definition injection framework built for the foundation. Concrete private test-only purpose/tool variants provide integration coverage before the first production purpose exists, under the fixture boundaries below.

### Public and harness boundaries

- The integration surface is `harness.sessionExists({ id }): Promise<boolean>`, `harness.createSession({ id, instructions, enabledTools }): Promise<void>`, the exported `toolDefinitions` catalog of `{ name, description, inputSchema }` descriptors, `portfolio.agentInteractions.find({ agentInteractionId })`, `portfolio.agentInteractions.run({ agentInteractionId })`, and `portfolio.tools.invoke({ agentInteractionId, name, arguments })`. The harness request's `id` is the AgentInteraction ID and `enabledTools` contains Core tool names. Find returns the full record through Core's Result; run and invoke also return Core Results. The Consumer supplies trusted interaction identity to invoke, while the agent supplies only the tool name and arguments.
- Consumers supply session-existence lookup and creation through `CoreDependencies.harness`. Public interaction operations are Consumer-authorized find and explicitly user-triggered run and repair by interaction ID. Initial record creation stays internal to purpose-specific Core operations; run does not create another AgentInteraction, while repair creates a replacement under its eligibility guards. Consumers cannot register arbitrary domain definitions or acceptance handlers.
- `CoreDependencies.harness` is required when opening Core, including for Consumers using only non-interaction operations. Opening validates the adapter's required `sessionExists` and `createSession` methods without invoking either, creating a session or probing the harness. Core exposes one complete dependency contract rather than an optional harness configuration that fails only when an operation needs it.
- Find returns the full AgentInteraction record, including saved instructions, not harness transcripts or execution state.
- Read and tool-invocation errors distinguish an absent interaction (`not-found`, resource `agent-interaction`, with `id`), tool access to a closed interaction (`agent-interaction-closed`, with `agentInteractionId`), an unknown catalog name (`unknown-tool`), and a known tool unavailable for the purpose (`tool-not-allowed`). Malformed invocation or tool arguments use the existing `invalid-input` contract. Existing storage/internal errors and each tool's domain errors remain applicable, without raw diagnostics. Find may return a closed interaction.
- Consumers route conversation directly to the harness and configure native tools and sandbox permissions. The harness controls its internal runs. Conversation alone does not save or accept domain proposals, and native-tool access does not grant Core domain authority. Preventing alternate access through authenticated entry points is a [deferred tools-design question](FUTURE.md#native-tool-authority-bypass); the Core tool allowlist alone is not a harness-wide sandbox.
- Core exposes its tool catalog and invocation boundary for Consumers to wire into supported harnesses. Tool registration and the transport back to Core belong to the Consumer integration, not the session-creation request; live handlers are not passed across the process boundary during creation.
- Core authors tool argument contracts as validation pipes so handler input types are inferred from the parsed values. Core maps those pipes to JSON Schema when constructing the exported tool catalog; Consumers import names, descriptions and already-generated input schemas, not the internal pipes or handlers. The pipe remains the single source for schema generation and authoritative runtime validation, without a separately maintained schema. Trusted session identity and Portfolio selection are outside the agent-visible argument contract.
- The harness session ID is always the AgentInteraction ID. Core supplies that ID when requesting session creation; the Consumer harness API must enforce the same identity. Core stores no separate session ID, harness-instance identifier or namespace. Selecting the correct integration, including after import, is the Consumer's responsibility. Core trusts that integration to prevent duplication without deduplication machinery, retention-window tracking or capability probes.
- Ordinary interaction reads and import do not trigger harness calls or repair lifecycle state.

### Record creation and explicit run

- AgentInteraction contains `id`, `purpose`, `instructions`, `created: AuditStamp`, `closed` and `repaired: { stamp: AuditStamp; agentInteractionId: Id } | null`. It does not persist a separate startup-confirmation field.
- The terminal field is `closed`: `null` while unfinished, `{ type: 'success', stamp: AuditStamp }` for success, or `{ type: 'failure', stamp: AuditStamp, reason: FailureReason }` for failure. Failure reasons are Core-defined structured variants covering failed session creation and purpose-specific failures, not arbitrary diagnostics; only failure carries a reason. The outcome, stamp and any failure reason are recorded atomically.
- Session-creation failure uses `reason: { type: 'session-creation-failed' }`, without raw harness diagnostics.
- Purpose is a Core-owned discriminated union whose variants contain their required target references and domain details. AgentInteraction has no separate target field. The purpose owns the relationship; target records do not store a reverse or current AgentInteraction reference. Core derives the target, instructions, enabled tools and target/purpose reservation identity from the purpose. Neither run nor tool invocation requires a target-side pointer back to the interaction; purpose-specific domain gates still apply.
- The calling domain operation supplies the resolved purpose, including its target reference, not a separate context string or tool list. The instruction builder takes only that purpose and the interaction ID, performs no domain-record or external reads, and produces one instruction string containing the task, constraints and necessary domain details. Core saves that text with the interaction. The purpose must therefore contain the resolved content needed for instruction construction, not merely references requiring later expansion. The saved request excludes tools, which are inferred from purpose. Creating the interaction does not invoke the harness or schedule an implicit run.
- When one domain operation creates both a target record and its AgentInteraction, they commit in the same explicit transaction: either both are saved or neither is. That operation returns its domain/storage outcome without harness-start or failure-closure errors. A later run failure does not roll back or delete the committed target.
- `portfolio.agentInteractions.run({ agentInteractionId })` first loads and validates the existing open interaction, then calls `harness.sessionExists({ id: agentInteractionId })`. If the session exists, run succeeds without calling create or replaying instructions. If it does not exist, run calls `harness.createSession` with the saved instructions and purpose-derived enabled Core tool names, then waits for the adapter's completion acknowledgment before returning success. It is a separate user-authorized action and owns harness-related errors and any failure-closure persistence errors. After success the Consumer can open the session using the AgentInteraction ID; Core does not perform UI redirection. A failed lookup is not evidence of absence.
- `harness.sessionExists({ id }): Promise<boolean>` is a read-only existence check returning an ordinary boolean, not a session payload or Core Result. A `true` result guarantees the same-ID session is fully established under the same conditions as creation acknowledgment: its requested Core tools are wired and enabled, with other Core tools disabled. Allocation or visibility of a session record alone is insufficient; this guarantee does not certify completion of the agent's work. A `false` result means the session is absent. Pending, partial or indeterminate creation must reject lookup rather than report `true` or false absence. Core validates the returned boolean and trusts the Consumer adapter's establishment guarantee before choosing the existing-session or creation path; it adds no separate readiness probe. A throw, rejection or malformed return is not converted to `false`; the check itself performs no creation, instruction replay or lifecycle repair.
- If `sessionExists` throws, rejects or returns a nonboolean, run returns `agent-interaction-lookup-failed` with `agentInteractionId` and no raw diagnostics. That invocation neither calls create nor writes interaction lifecycle, including a startup-failure closure. It does not overwrite a concurrent operation's outcome. A later explicit run remains possible if the interaction is still open; no automatic retry is performed.
- Run's success value is `void` in Core's Result. It does not return a duplicate session ID, interaction record or harness-specific URL; the Consumer already has the ID needed to open the established session.
- Run distinguishes `agent-interaction-start-failed`, when the harness creation call failed and failure closure was saved or an existing terminal outcome preserved, from `agent-interaction-closure-failed`, when that creation failure was followed by a storage failure that prevented confirmation of closure. Both errors carry `agentInteractionId` without raw diagnostics. Closure-failed does not assert that the interaction is closed, its reservation released or new tool calls disabled. These run-specific errors supplement existing input, not-found, closed-interaction and storage/internal errors; they do not belong to the original domain-creation operation.
- Repeated run of an open interaction with an existing session succeeds through the lookup path without replaying instructions, creating a replacement session or starting another agent turn. The existence check does not eliminate concurrent lookup/create races: the Consumer harness API still prevents duplicate sessions and instruction replay for the supplied ID. Core does not implement a run/resume controller. Run does not reopen a closed interaction.
- The Consumer adapter maps the prepared instructions to the harness's native request without loading or interpreting domain records. Domain details embedded in startup instructions are not authoritative current state; bound Core tools continue to read current permitted data.
- Session creation passes the interaction ID, prepared instructions and purpose-derived enabled Core tool names. The Consumer harness API enables only those Core tools for that session and disables all other Core tools. This allowlist does not restrict harness-native tools, which remain Consumer-configured.
- Creation succeeds only once the session exists with the required identity and its requested Core tools are wired and enabled, with other Core tools disabled. A queued launch alone is not success. The acknowledgment does not wait for the agent's work to finish or certify domain completion.
- The harness creation method returns `Promise<void>`: fulfillment acknowledges that the session is established, whether newly created or already present; a synchronous throw or promise rejection follows the failure-closure path. Core awaits completion and ignores any fulfilled return value rather than validating it or interpreting it as a session payload or Core Result. This does not change validation of the boolean returned by `sessionExists`, which controls run's branching. Startup-failure closure carries the authorizing run operation's AuditStamp, not the original creation stamp or a RuntimeRecord.
- Successful run requires no startup-confirmation write. It does not close the interaction or change an existing terminal outcome. Any failure closure uses an explicit transaction; no transaction or database lock spans either harness lookup or creation.
- After a harness creation failure, the closure transaction returns internal success only after saving the failure closure or confirming and preserving an existing terminal outcome. Await successful transaction settlement before constructing `agent-interaction-start-failed` outside the transaction; returning that public failure from the transaction callback would abort the closure. If persistence or transaction settlement prevents confirmation of closure, return `agent-interaction-closure-failed` instead, without claiming that authority ended or the reservation was released.
- Core's universal policy is at most one open interaction per purpose type and target within a Portfolio; individual workflows cannot opt out. An interaction occupies that pair while `closed` is null, including before run is called and while session creation is pending. Creation or repair rejects an observed open interaction for that pair; repeated run of the existing interaction is distinct and allowed. Different targets remain independently eligible. The policy is checked in code, not guaranteed against concurrent check-and-insert races; that limitation is [accepted for now](FUTURE.md#interaction-reservation-concurrency). Deliberately allowing multiple open interactions for the same pair requires a separately revisited design, not a configurable exception.
- Reservation identity is the purpose type and its target identity within the Portfolio, not the complete purpose payload. Different instructions, context details or referenced versions do not permit another open interaction for that same purpose type and target.
- Enforce the one-open-interaction policy in Core code: during creation or repair, query interactions for the same purpose type and target within the Portfolio, validate the returned records and reject an existing open interaction before insertion. Keep the check with the transaction's required writes. Do not encode this policy in a storage-level unique constraint or duplicate the relationship on the target; a future policy change should not require removing a database uniqueness constraint. Add no check-and-insert coordination in the current scope: concurrent calls may both observe no open interaction and commit distinct open interactions. A transaction alone does not establish exclusion.
- Verify observed-conflict refusal and required transaction atomicity with real storage. Do not require or claim universal exclusion between competing creators under the accepted race. Preserve the guarded update that prevents two repairs of the same failed interaction from committing separate replacements; it is distinct from purpose/target exclusivity.
- Failed session creation is represented by a failure closure with a structured startup-failure reason. Return a safe error and the saved interaction ID, not raw harness diagnostics or a claim that the committed interaction rolled back. Do not claim closure was persisted if its storage write fails. There is no implicit session replacement, retry, timeout release or recovery queue. Deferred recovery decisions live in [FUTURE.md](FUTURE.md#deferred-decisions).
- A creation call that throws or rejects, including a timeout reported by the adapter, triggers startup-failure closure even when the session may already exist. The reason records failure of the creation call, not proof that no session exists. Persist closure only if the interaction is still open; preserve any existing terminal outcome. Once closure is persisted, an existing or late-created session cannot make new Core tool calls, though it may continue running independently. This adds no Core timeout policy, automatic retry or replacement session.
- Overlapping run calls follow the same creation-failure rule independently: a failed creation call closes a still-open interaction even if another run has already succeeded or later succeeds. Success never reopens the interaction or overwrites a terminal outcome. No additional run-coordination machinery is introduced. A failed overlapping creation request can therefore end Core tool authority for an otherwise established session, leaving recovery to explicit repair under its eligibility guards.

### Tools and closure

- Infer enabled Core tool names from the persisted purpose; do not persist a separate tool list, schemas or handlers. Each invocation uses trusted session identity supplied by the Consumer integration, not agent-controlled arguments, to bind authority to the exact interaction and target. Core validates arguments and enforces purpose and lifecycle eligibility independently of harness tool filtering. Human-only acceptance operations are not agent tools.
- Core exposes one Portfolio-scoped tool invocation entry point accepting the trusted session ID, tool name and arguments. The Consumer bridge selects the authorized Portfolio and supplies session identity from its harness integration; the agent cannot choose or override either, and an interaction ID alone is not a credential. Each call loads the persisted interaction, derives its target and allowed tools from purpose, checks lifecycle and validates arguments before executing under domain rules. Authority does not depend on retaining per-session handlers or closures across process restarts.
- Tool-driven writes use the attribution bound to the Consumer bridge's Portfolio through the existing attribution mechanism, not the interaction creator's stored attribution. The Consumer binds attribution appropriate to the agent/session, and Core timestamps each invocation. Agent arguments cannot supply or override attribution; attribution remains distinct from the trusted session identity and purpose-based authority checks.
- After the interaction commits, scoped context reads may execute while session creation is pending. They return current permitted data and record/version identities where applicable without rewriting the saved instructions or advancing domain state. Purpose-specific domain gates remain authoritative rather than trusting earlier reads.
- Closure depends on the applicable domain conditions, not a persisted startup acknowledgment. An interaction may close before the session-creation call settles; a late response must not reopen it or overwrite its terminal outcome.
- Every terminal closure conditionally updates only `closed`, requiring the exact interaction ID and `closed === null` at the write itself. Preserve that predicate through the storage write and validate the returned match count; an earlier open-state read is insufficient. Domain completion and its guarded closure commit in the same transaction, and losing the guard aborts that completion. A delayed run-failure handler instead confirms and preserves an existing terminal outcome under the run failure contract. Never overwrite the whole interaction or its repair information. Closure releases the reservation through terminal state; there is no target-side interaction reference to clear or replace.
- Both success and failure are terminal closure outcomes within the current Portfolio history: the interaction remains closed and no longer occupies its unfinished target/purpose reservation. Tool-access rules apply equally to both outcomes. Explicit [Snapshot restoration](#snapshots-and-maintenance) can replace that history with an earlier lifecycle state.
- Purpose-specific terminal failures are recorded by authorized domain operations. The startup path additionally records failed session creation as a failure closure. An ordinary tool error or later harness execution error does not itself establish a terminal domain failure.
- Closure blocks new interaction-bound Core tool calls, including reads, even when the harness retains an earlier binding. Reads that passed their lifecycle check before closure may finish afterward; closure does not cancel them. Strict coordination of already-admitted tool writes with concurrent closure is [deferred](FUTURE.md#tool-write-and-closure-coordination): the admission check alone does not guarantee that an in-flight write cannot commit after closure. Preserve domain atomicity, purpose checks and reservation guards independently.
- Closing the interaction neither closes the harness session nor deletes the transcript. Separately Consumer-authorized queries remain available. Late startup acknowledgment cannot reopen a closed interaction or reclaim its reservation.
- Exercise the actual shared infrastructure with concrete private purpose/tool variants enabled only during tests and real Equipped InMemory storage, including lifecycle, run, repair, purpose/target reservations, tool authority and Snapshot behavior. Fixtures supply only concrete purpose/tool behavior and test data; they pass through the real schema validation, instruction construction, internal creation, operation dispatch, transactions and Snapshot parser rather than bypassing validation or replacing shared logic with test-only implementations. Outside tests, reject fixture purposes, including on storage reads and Snapshot import, and exclude fixture tools from the exported catalog and invocation dispatch. Verify those production exclusions. Fixtures must not become public purposes, public test hooks or Consumer extension points. No particular target domain's workflow is required to verify the reusable foundation; do not introduce Consumer registration, a generic purpose-injection framework or a generic composition boundary solely for tests.

### Explicit repair

`portfolio.agentInteractions.repair({ agentInteractionId })` identifies the failed interaction and returns the full replacement AgentInteraction through Core's Result. The replacement's `created` stamp comes from the repair operation; the Consumer uses its new ID for a separate explicit run.

Only an interaction closed with `type: 'failure'`, `reason.type: 'session-creation-failed'` and `repaired: null` is eligible for user-triggered repair. Eligibility is derived from the failure reason and repair record, not a persisted `repairable` flag. Core must also enforce the applicable purpose-specific domain rules and purpose/target reservation; an eligible reason does not guarantee repair succeeds. Purpose-specific failures remain governed by their domain workflows.

Repairability is an internal AgentInteraction operation rule, not a record-pipe constraint. Pipes validate the shapes of `closed` and `repaired` independently; do not add cross-field validation requiring a repair record to accompany a particular failure reason on storage reads or import. The repair operation owns eligibility enforcement.

`repaired` is a nullable embedded record on the failed interaction: null means it has not been repaired; otherwise `stamp` records the authorizing repair operation and `agentInteractionId` identifies the replacement, not the failed interaction itself. New interactions, including replacements, begin with `repaired: null`.

After loading and validating the interaction, repair checks `repaired` first. A non-null record returns `agent-interaction-already-repaired` with the failed interaction ID and its recorded replacement ID. Otherwise, repair errors distinguish an ineligible terminal state or failure reason (`agent-interaction-not-repairable`) and another open interaction holding the purpose/target reservation (`agent-interaction-already-open`). Existing input, not-found and storage errors remain applicable. Repeated repair returns the already-repaired error rather than creating or running another interaction or silently returning the replacement as success.

Repair atomically creates a new open AgentInteraction with a new ID and the same purpose and sets the failed interaction's `repaired` record with the repair stamp and replacement ID. The failed interaction's purpose, instructions, creation stamp and failure closure, along with historical references, remain unchanged. No reverse relationship on the target is rewritten. Check for an existing open interaction in the transaction; replacement creation and the repair record update guarded by `repaired === null` commit together or not at all. That guard prevents duplicate repair of the same failed interaction, not the accepted purpose/target check-and-insert race against other creation paths. Repair makes no harness call; the replacement requires a separate explicit run.

If repair loses the conditional `repaired === null` update, roll back its transaction before rereading the original interaction once from storage, outside the aborted transaction. Validate the reread; a non-null `repaired` record returns `agent-interaction-already-repaired` with the original interaction ID and the recorded winning replacement ID. If rollback fails or the reread cannot establish that outcome, return `storage-operation-failed` without raw diagnostics or a claimed winner. This read classifies the lost guard; it does not retry the mutation, create another replacement or reinterpret unrelated storage failures as repair conflicts.

Repair rebuilds and saves instructions using only the saved purpose and replacement interaction ID, through the same purpose-specific builder as initial creation, rather than copying the failed interaction's instruction text verbatim. Instruction reconstruction fetches no additional domain records or external data; it does not require historical records to remain available for rendering. Preserve the purpose's target references, versions and resolved domain details; do not silently substitute newer data. Any interaction identity embedded in the rebuilt instructions refers to the replacement. This self-contained rendering does not remove the repair operation's storage reads, eligibility checks or transaction requirements.

### Snapshots and maintenance

Introduce the AgentInteraction model and storage migration together with its Snapshot export/import handling, including record validation, AuditStamp conversion and atomic replacement. A migration level must not advertise support for interaction storage while its Snapshot implementation omits those records or leaves the destination interaction collection outside replacement. This includes clearing existing interactions when importing an empty interaction collection.

Snapshot import preserves interaction identities, lifecycle and saved startup requests. Preserving the interaction ID also preserves the original session ID. Access follows imported lifecycle and ordinary authorization checks through the destination's configured dependency; import makes no harness calls and adds no recovery mechanism. Source and destination may refer to the same session.

Import preserves purpose, exact saved instructions, closure outcome and failure reason, and the replacement ID in `repaired`. Convert `created`, `closed.stamp` and `repaired.stamp` where present using the existing imported AuditStamp convention: preserve original event times, remove source-local attribution and record the current import time. Keep null `closed` and `repaired` fields null; import does not run or repair an interaction.

Restoring an earlier Snapshot can replace a closed interaction with its earlier open state. Its surviving harness session can then regain Core tool access without another run, subject to ordinary authorization and purpose gates. Restoration can also roll back repair metadata; when repair is available, eligibility follows the restored records rather than repair history outside that Snapshot. Closure terminality and single-use repair therefore apply within the current history, not across explicit restores. This is an accepted consequence of exact Portfolio replacement: Consumers must treat restoration as an authority-changing action. Import does not rewind, cancel or reconcile surviving harness sessions or their external effects.

Consumers drain whole in-flight operations for maintenance, including pending harness calls and subsequent database work, and prevent new bound Core tool calls while maintenance runs. This does not require closing harness sessions. See [operation boundaries](BOUNDARIES.md).

Core shutdown rejects new operations and tool calls, but drains an already-admitted run operation through settlement of the harness call and any resulting failure-closure write before releasing storage. Shutdown itself does not cancel the harness session or close the AgentInteraction; it leaves the session running independently.

## Snapshot and Secret documentation contracts

- Distinguish Core-owned Stored Secret Values and Portfolio Secret Protection from Consumer encryption-key provisioning. Core-owned protection and Snapshot export/import are implemented; the package README owns usage and verification scope. Do not describe Consumer codec callbacks or external-store references as the current Secret API.
- Portfolio Import requires a ready Portfolio and means atomic replacement with preserved imported identities and relationships, not initialization or record merging. Snapshots always include Secret values under passphrase encryption, never the Portfolio encryption key. Import uses the destination's opening key or explicit plaintext mode, never a per-import replacement key.
- Snapshots carry the source's final validated catalog migration ID, not a restorable migration ledger. Export captures that ID with the data; import revalidates destination history inside the replacement transaction and requires an exact recognized ID match before writes. Never infer migration order from timestamps, overwrite the destination ledger or convert mismatched Snapshots.
- Import validates payload and record schemas, not cross-record relationships or graph consistency; do not add duplicate-ID constraints, deduplication, a relationship audit or data repair. Preserve exported domain data except conversion of Audit Stamps to imported attribution and the agreed Secret-value reprotection under the destination's opening key/mode. Snapshot authentication, migration compatibility and atomic storage-failure handling still apply. Schema-valid data is not a certification of relational integrity.
- Imported Audit Stamps use `{ src: 'imported', at, iat }`: preserve the original `at`, remove `by`/`cid`, and refresh `iat` to this import's time on every import, including already-imported stamps. Subsequent local operations create ordinary local stamps.
